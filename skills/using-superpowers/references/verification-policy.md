# 分级验证策略（定制版，版本 1）

本文件是全部技能、主代理、实现者和审查者共用的验证规则。用户要求和项目必需检查优先；任务策略必须符合本规则，其他技能不得恢复无条件 TDD 或完整套件要求。

## 入口与任务等级

brainstorming、writing-plans、executing-plans、subagent-driven-development 仅由用户原生命令启动。普通需求、规格或计划获批、计划文件存在、其他技能要求和子代理指令都不能启动这些阶段。每个阶段只交付自身产物。普通直接开发也先简短记录等级和验证方式，不为此调用正式规划技能。

先评估出错影响，再评估不确定性和实现复杂度。权限、资金、数据迁移、并发安全、公共接口、影响广泛或难撤销的改动默认 high；明确局部、低影响且易撤销的任务可选 low；其余默认 medium。同一计划允许混合等级。新增具体风险时记录重新定级的依据；不能只为获得预算而升级。

| 等级 | 验证方式 | 默认额度 | 审查 |
|---|---|---|---|
| low | 代码核查＋最小编译、语法或结构检查 | 一次实际检查机会，无红灯和修复重跑 | 实现者自查 |
| medium | 必要编译和相关单元测试集中运行 | 一轮初始验证＋最多两轮定向修复验证 | 批次集中审查 |
| high | 关键行为、相关回归和必要集成检查 | 每批次最多一轮红灯、一轮初始绿灯、两轮定向修复；全计划集中一轮完整验证 | 关键任务独立审查＋最终审查 |

medium 只有在策略写明行为红灯及理由时才另配一轮红灯。high 也不要求配套文案和配置逐项红灯。一轮是事先登记的检查集合，每项最多运行一次，同时记录实际命令数；串联命令、内部重试循环、换工具或换代理不能绕过预算。检查命令本身的测试框架并行不增加轮次，但禁止在命令中偷偷重复整套检查。

low 的检查放在全部实现及自查之后。失败、超时或命令启动失败都消耗机会；失败后不得宣布完成。继续修复会使原证据失效，追加检查必须获得用户明确的预算调整。纯文档和配置用一次有效语法或结构校验；无有效工具时报告未验证，不安装工具或用无关命令制造通过结果。

项目必需检查、工作树基线检查、领域检查和最终验证在规划时分配额度；有冲突先说明并由用户调整预算。预算耗尽后记录未解决问题并停止运行，不降低完成标准。最终审查发现集中修复，最多两轮定向验证，计入对应任务剩余 repair 额度，不开新预算。真实严重缺陷不能靠搁置变成完成。

## 红灯与验收

采用 red-green 时必须事先写出可观察行为、预期结果、预期失败原因和证据价值。缺失模块、函数未定义、导入错误、语法错误及故意失败断言都不是行为红灯；此类运行仍消耗额度且标为失败。禁止为补流程删除已有实现、制造占位功能或反复切换版本。

代码核查检查需求、差异、调用关系和适用边界。编译通过只证明编译检查通过，不证明业务正确。实现后测试可以验证普通新功能；真实缺陷复现和关键规则优先使用行为红灯。验收行为与验证方式分开记录，测试须保留独立断言，相关功能合并运行批次。

## 策略格式与辅助程序

在计划头部放全局默认策略，在每个任务内放完整有效策略，均使用标记为 verification-policy 的 JSON 代码块。任务字段：version（1）、task（任务标识）、level（low/medium/high）、reason、mode（compile/batch/red-green）、acceptance（验收清单）、review（self/batch/independent）、scope（仓库内相对路径数组）、checks（检查数组）。全局块使用 defaults，task-brief 将它带入简报；脚本只执行任务的完整块，避免隐式继承遗漏。

每个检查包含 id、kind（compile/unit/integration/full/behavior）、command（可执行文件）、args（参数数组）、timeoutMs（正整数）。使用 shell 时显式把 shell 作为 command，把脚本作为参数；不要自行拼接跨平台字符串。low 只登记一个 compile 检查。mode=red-green 还须有 red 对象：behavior、expectedFailure、value、check（检查 id）、failurePattern（匹配真实行为断言失败的正则）。

~~~verification-policy
{"version":1,"task":"1","level":"medium","reason":"三个相关业务功能，影响可控","mode":"batch","acceptance":["正常路径","错误参数"],"review":"batch","scope":["src","tests","package.json"],"checks":[{"id":"compile","kind":"compile","command":"node","args":["--check","src/example.js"],"timeoutMs":60000},{"id":"unit","kind":"unit","command":"node","args":["--test","tests/example.test.js"],"timeoutMs":60000}]}
~~~

辅助程序位于本技能 scripts/verify.mjs，Node.js 20+，仅用内置库：

~~~text
node verify.mjs init PLAN_OR_POLICY_JSON WORKSPACE
node verify.mjs run WORKSPACE TASK ROUND PHASE CHECK ROLE
node verify.mjs status WORKSPACE
node verify.mjs complete WORKSPACE TASK
node verify.mjs amend WORKSPACE TASK POLICY_JSON AUTHORIZATION
~~~

PHASE 为 red、verify、repair、final；ROUND 是控制者分配的唯一编号。同轮登记检查每项只运行一次。verify 首轮和 final 完整验证必须覆盖任务声明的全部对应检查；repair 只跑明确覆盖修复的子集。final 仅 high 可用，全计划一次，所有任务完成代码后集中执行。基线检查不另设隐藏额度，显式列入策略的检查和预算。任务不得在仍有失败、正在运行或过期证据时完成。

init 不重置已有预算；amend 记录用户预算调整原文，保留运行历史。程序无法证明授权文字来自人类，控制者必须核对来源；普通代理建议不算授权。不支持辅助程序的平台用相同字段人工记账，不自动安装 Node，也不声称平台强制执行。

## 证据与角色

控制者唯一负责策略和轮次分配。实现者、审查者共用工作区账本；换代理、切换执行方式、恢复会话和失败都不重置预算。并行运行通过工作区锁和登记编号防止重复领取。审查者默认读取日志及差异，发现已有结果无法回答的具体问题时交给控制者登记检查或申请预算调整。

记录实际命令、执行角色、退出状态、完整日志、覆盖范围、轮次、代码与策略指纹。相关源码、依赖、构建配置或已登记命令改变使证据失效。scope 必须包含这些文件；禁止通过缩小 scope 复用过期证据。提交、代理交接、汇报不改变有效性。完成验证和分支收尾复用有效证据；合并导致相关内容改变才重新评估，追加运行仍受预算限制。

审查核对实际需求和具体风险，不能因没有 TDD、每函数测试或完整套件单独判错。报告列明已验证范围和未验证项，严重缺陷或预算耗尽不能报告完成。完成报告生成前不删除日志；默认保留被忽略的 .superpowers 验证目录，清理需用户要求。

旧计划没有策略时，当前已手动启动的执行者先按本规则记录完整任务策略，再继续；不调用 writing-plans，不机械执行旧式红绿步骤。辅助脚本若遇到缺少完整策略则明确报错，不生成假通过结果。
