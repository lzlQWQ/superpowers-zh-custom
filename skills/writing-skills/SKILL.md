# 编写与维护技能

本节是 superpowers-zh 的增量内容：技能修改按风险做行为验证，不逐文件制造红绿仪式。

## 设计

读取 [分级验证策略](../using-superpowers/references/verification-policy.md)。先理解用户目标、现有技能路由、入口、支持资源、平台引导和消费者。跨技能改造先检查整体依赖，再修改局部。全局行为修改默认 high；局部排版或参考修正可 low。

技能是可复用方法或参考，不是某次工作叙事。描述简短、只解释适用条件；正文给有用的判断和动作，细节进入按需参考，确定性重复操作才编写脚本。不为一般能力增加通用限制。保留已有元数据，显式-only 只在用户要求时设置。

## 验证

先确定可观察行为和运行预算。复杂行为修改做现有规则与新规则的同场景对照；不是让每个 Markdown 文件都先失败。聚焦真实触发、执行次数、交接、失败处理与验收证据；文本和字段检查只能证明结构，不能代替消费者行为。

需要独立评估且有授权时，给全新子代理最小任务与技能，说明允许的副作用，不告诉它期望答案；结果区分只读模拟与真实宿主调用。将相关场景合并评估，默认一轮集中验证，失败后最多两轮定向修复验证，不重复五次措辞采样或测试直到“无懈可击”。

红灯只有现有规则在真实行为上表现出缺口时才有价值。代码不存在、导入错误或故意失败不算红灯；普通文档和编译检查允许实现后验证。用户预算优先，不删除已写内容重来。

## 维护与交付

检查名称、描述、引用、平台元数据、脚本实际运行和分发结果。保持中文内容，标明有意定制，避免上游同步恢复旧规则。报告实际测试范围、限制和证据，未完成宿主验收不能声称行为全部通过。不自动提交、推送、发布或创建 PR。

写作与评估参考按需要阅读 [测试场景](testing-skills-with-subagents.md)、[劝服原则](persuasion-principles.md)、[编写实践](anthropic-best-practices.md)；其中旧的无条件 TDD 示例不覆盖共用策略。
